# Vibe Venture

Учебный full-stack пет-проект для GitHub-портфолио: лендинг вымышленной венчурной фирмы **Vibe Venture** с формой заявки, API-роутом, серверной валидацией, хранением в SQLite и CSV-выгрузкой.

> **Статус: заявки сохраняются в SQLite и выгружаются в CSV.** Страницы `/` и `/about` свёрстаны в финальной дизайн-системе и проверены на ширинах 375, 768 и 1440 px. Правила заявки описаны одной Zod-схемой (`src/lib/applicationSchema.ts`). Форма проверяет данные этой схемой и отправляет их в `POST /api/applications`. Сервер проверяет их той же схемой и сохраняет в локальную базу `data/app.db`. Команда `npm run export:csv` выгружает все заявки в `exports/applications.csv`, пример выгрузки с вымышленными заявками лежит в репозитории (`exports/sample-applications.csv`). Проект в SourceCraft пока не опубликован. Пошаговая проверка — в разделе [Проверка проекта](#проверка-проекта).

## Проверка проекта

Обязательный сценарий: запустить проект, отправить заявку через форму, найти её в SQLite и в CSV-выгрузке. Команды одинаковы для macOS (Terminal) и Windows (PowerShell), отличия указаны отдельно. Подробности установки — в разделах [Запуск на macOS](#запуск-на-macos) и [Запуск на Windows](#запуск-на-windows).

**Требования:** Node.js 22 LTS или 24 LTS (минимум 20.17 — его требует пакет `sqlite3`), npm, Git.

1. **Установка.** Склонируйте репозиторий, перейдите в папку проекта и установите зависимости:

   ```bash
   git clone <url-репозитория> vibe-venture
   cd vibe-venture
   npm install
   ```

2. **Запуск.** Запустите dev-сервер и откройте [http://localhost:3000](http://localhost:3000):

   ```bash
   npm run dev
   ```

   Вместо dev-сервера можно проверить production-сборку: `npm run build`, затем `npm run start`.

3. **Страницы.** На главной `/` пять секций: «Главная», «О нас», «Плюсы», «Вопросы», «Форма». Ссылки в шапке ведут к секциям, ссылка «Подробнее о Vibe Venture» в секции «О нас» — на `/about`.

4. **Заявка.** В шапке нажмите «Подать заявку» или прокрутите до секции «Форма».
   - Нажмите кнопку «Подать заявку» под формой, не заполняя поля: под каждым обязательным полем появится ошибка и сообщение «Проверьте отмеченные поля. Ошибок: 5.», запрос на сервер не уйдёт.
   - Заполните поля:

     | Поле | Пример |
     | --- | --- |
     | Имя основателя | Анна Проверка |
     | Контактный email | anna@example.com |
     | Название проекта | Vibe Notes |
     | Стадия проекта | MVP |
     | Описание проблемы | Командам поддержки трудно находить ответы. |
     | Демо или репозиторий | можно оставить пустым или указать `https://example.com` |

   - Нажмите «Подать заявку». Должно появиться сообщение «Заявка успешно отправлена». Повторный клик по кнопке новую запись не создаёт.

5. **SQLite.** При первой заявке создаётся файл `data/app.db`. Во втором терминале, из корня проекта, выведите последние записи. Команда использует установленный пакет `sqlite3`, поэтому работает и на macOS, и на Windows без отдельной программы:

   ```bash
   node -e "const s=require('sqlite3');const db=new s.Database('data/app.db',s.OPEN_READONLY);db.all('SELECT id, founder_name, email, stage, created_at FROM applications ORDER BY id DESC LIMIT 5',(e,r)=>{if(e)throw e;console.table(r)})"
   ```

   Первой строкой будет только что отправленная заявка. На macOS можно также использовать системный консольный `sqlite3` (см. [Хранение в SQLite](#хранение-в-sqlite)).

6. **CSV.** Выгрузите заявки:

   ```bash
   npm run export:csv
   ```

   Скрипт выведет количество заявок и путь к файлу `exports/applications.csv`. Последней строкой в файле будет ваша заявка. Открыть файл: `open exports/applications.csv` на macOS, `Invoke-Item exports\applications.csv` на Windows.

7. **Пример выгрузки.** Файл [`exports/sample-applications.csv`](exports/sample-applications.csv) из репозитория — результат того же скрипта на отдельной временной базе с четырьмя вымышленными заявками. По нему можно проверить формат без запуска проекта: заголовки, кириллицу, BOM, экранирование запятых, кавычек и переносов строк, пустой `demo_url`. Команда `npm run export:csv` этот файл не трогает.

8. **SourceCraft.** Ссылка на рабочую версию пока не добавлена (см. [SourceCraft](#sourcecraft)).

Сервер можно не останавливать на шагах 5–6: команды только читают базу. Остановить сервер — `Ctrl + C`.

## О проекте

### Легенда

Vibe Venture — небольшая венчурная фирма, которая работает с ИИ-стартапами на ранней стадии.

Фирма ищет команды, у которых есть понятная проблема и прототип или MVP. Таким командам она может предложить:

- микрогрант;
- продуктовую обратную связь;
- помощь с упаковкой питча;
- первые пилотные интро.

**Целевая аудитория:** основатели ИИ-стартапов.

**Цель сайта:** объяснить, что предлагает фирма, и собрать заявку на первичный отбор.

### Чего на сайте нет

Компания вымышленная. На сайте не должно быть:

- реальных или выдуманных инвестиционных сделок и портфеля компаний;
- сумм финансирования, в том числе размера микрогранта;
- сроков рассмотрения заявок;
- гарантий инвестиций или обещаний результата.

Формулировки должны оставаться нейтральными: «может предложить», «по итогам первичного отбора» и т. п.

---

## Основной пользовательский сценарий

1. Основатель ИИ-стартапа открывает главную страницу `/`.
2. Из первого экрана понимает, кто такие Vibe Venture и для кого они работают.
3. Читает секции «О нас», «Плюсы» и «Вопросы». При желании открывает `/about` с подробным описанием фирмы.
4. Через навигацию или CTA-кнопку переходит к секции «Форма».
5. Заполняет шесть полей. Клиентская проверка подсвечивает ошибки до отправки.
6. Отправляет форму, браузер делает запрос `POST /api/applications`.
7. Сервер проверяет данные той же Zod-схемой:
   - данные валидны — заявка сохраняется в SQLite, пользователь видит «Заявка успешно отправлена»;
   - данные невалидны — сервер возвращает ошибки по полям, форма их показывает.
8. Владелец проекта локально запускает скрипт и получает CSV со всеми заявками.

Ссылки построены через `next/link` в виде `/#...`, поэтому работают и со страницы `/about`. На страницу `/about` ведут ссылки из секций «О нас» и «Вопросы» и из подвала. Шапка липкая. ### Форма заявки

✅ Реализована как клиентский компонент `ApplicationForm` (`src/components/application-form.tsx`). На сайте одна форма, в ней шесть полей:

| Поле | Ключ | Элемент | Обязательное | Правила |
| --- | --- | --- | --- | --- |
| Имя основателя | `founderName` | `input type="text"` | да | 2–80 символов |
| Контактный email | `email` | `input type="email"` | да | корректный email, максимум 254 символа |
| Название проекта | `projectName` | `input type="text"` | да | 2–120 символов |
| Стадия проекта | `stage` | `select` | да | `idea`, `prototype`, `mvp` или `early_users` |
| Описание проблемы | `problem` | `textarea` | да | 10–1000 символов |
| Демо или репозиторий | `demoUrl` | `input type="url"` | нет | пусто или корректный URL с `http://` / `https://`, максимум 2048 символов |

Стадии и их подписи: `idea` — Идея, `prototype` — Прототип, `mvp` — MVP, `early_users` — Первые пользователи.

Все правила, лимиты, стадии и тексты ошибок заданы в `src/lib/applicationSchema.ts`. Форма их не дублирует:

- атрибуты `maxLength`, метки ограничений («2–80 символов») и счётчик «N / 1000» строятся из объекта `limits`;
- варианты `select` — из `stages` и `stageLabels`.

Длина считается после обрезки пробелов по краям (`trim` в схеме).

Как форма выглядит:

- Строгая сетка: 2 колонки с `sm`, описание и ссылка на всю ширину.
- Каждое поле — CSS subgrid из четырёх строк: подпись, подсказка, поле, ошибка. Поэтому линии полей в соседних колонках совпадают, даже если одна подсказка переносится на две строки или ошибка есть только у одного поля.
- Крупные подписи Oswald и короткие подсказки под ними. Ограничения по длине и формату («2–80 символов», «http:// или https://») — небольшая приглушённая метка справа от подписи. Она видна всегда, в том числе на мобильных без hover, и входит в `aria-describedby` поля вместе с подсказкой и ошибкой.
- Поля с нижней границей вместо рамки (класс `.field-input` в `globals.css`).
- Фокус — рамка 3px и жёлтая подложка.
- Ошибка — оранжевая нижняя граница 4px и текст на оранжевой плашке. Текст на плашке чёрный, контраст около 6,6:1.
- Скруглений и теней нет.

### Клиентская проверка

✅ Проверка через общую Zod-схему `applicationSchema`, той же, что на сервере. Значения хранятся в React-состоянии, библиотек форм нет.

- Проверяются обязательность, длина, формат email (`z.email()`), допустимость стадии и корректность необязательной ссылки (`new URL`, только `http:` и `https:`, в адресе хоста должна быть точка).
- Когда проверка срабатывает:
  - при уходе с заполненного поля проверяется это поле (`applicationSchema.shape[поле].safeParse`);
  - уже показанная ошибка пересчитывается при вводе и исчезает, как только значение исправлено;
  - при отправке вся форма проверяется через `applicationSchema.safeParse`, под каждым полем показывается первое сообщение из `z.flattenError`.
- Ошибка выводится под своим полем. У поля появляется `aria-invalid="true"`, а `aria-describedby` ссылается на подсказку, ограничение и текст ошибки.
- При ошибке введённые значения сохраняются, фокус переходит на первое ошибочное поле. В живой области (`aria-live="polite"`) появляется «Проверьте отмеченные поля. Ошибок: N».
- Если клиентская проверка не прошла, запрос на сервер не отправляется.
- При корректных данных форма отправляет их в API (см. «Отправка формы»).

### Отправка формы

✅ Форма отправляет данные в `POST /api/applications` через `fetch`.

- **Сетевая логика** вынесена в `src/lib/submitApplication.ts`. Функция `submitApplication(data)` делает запрос, разбирает ответ и возвращает форме один из трёх результатов: `success` с сообщением API, `invalid` с ошибками по полям или `error` с понятным общим сообщением. В самой форме сетевого кода нет.
- **Состояния формы** заданы явным типом: `idle`, `invalid`, `submitting`, `success` с сообщением, `error` с сообщением.
- **Порядок отправки:**
  1. Данные проверяются общей Zod-схемой. При ошибках запрос не уходит.
  2. На сервер отправляются уже проверенные значения с обрезанными пробелами. Сервер проверяет их той же схемой.
  3. Во время запроса кнопка показывает «Отправляем...» и получает `aria-disabled="true"`, курсор становится `progress`.
- **Почему `aria-disabled`, а не `disabled`:** при `disabled` браузер снимает фокус с кнопки, и пользователь клавиатуры теряет место в форме.

#### Защита от повторной отправки

Случайный двойной или тройной клик не создаёт дубликатов. Защита синхронная и не зависит от перерисовки React. Она построена на двух `useRef` в `ApplicationForm`:

- **`submitting`** — флаг «запрос в пути».
  - Ставится в `true` синхронно, до первого `await`, поэтому второй клик или `submit` в том же такте его уже видит.
  - Снимается в `finally` после любого исхода запроса.
- **`sentValues`** — объект значений, который последним успешно сохранился.
  - Каждое изменение поля создаёт новый объект `values`, поэтому сравнение `sentValues.current === values` мгновенно показывает, менялись ли данные после успеха.
  - Это работает и для клика, пришедшего между ответом сервера и перерисовкой.

`handleSubmit` сразу выходит, если запрос уже в пути или текущие значения уже успешно отправлены. Состояние `status` в `useState` отвечает только за отображение: текст и вид кнопки, сообщения.

| Ситуация | Кнопка | Повторная отправка |
| --- | --- | --- |
| Запрос выполняется | «Отправляем...», `aria-disabled`, курсор ожидания | Игнорируется (клик, Enter в поле, `requestSubmit`) |
| Успешная отправка, поля не менялись | `aria-disabled`, серая заливка (`bg-muted`), курсор `not-allowed`. Значения остаются в полях | Игнорируется |
| После успеха изменено любое поле | Снова активна, сообщение об успехе скрыто | Разрешена: это уже другая заявка |
| Ошибка сети или сервера, ошибки валидации | Активна, значения сохранены | Разрешена |

Проверено в Chrome настоящими событиями мыши, с подсчётом записей в SQLite:
- двойной клик с интервалом 0, 30, 80 и 250 мс и тройной клик с интервалом 30 и 100 мс — 1 запрос и 1 запись;
- `click` + `click` + `requestSubmit()` + событие `submit` в одном такте — 1 запрос.

| Результат | Что видит пользователь |
| --- | --- |
| Успех (`201`, заявка записана в базу) | Сообщение API на жёлтой плашке «Заявка успешно отправлена». Значения остаются в полях, кнопка отправки неактивна до изменения любого поля. Появляется кнопка «Очистить форму» |
| Ошибки валидации с сервера (`400` с `errors`) | Сообщения под соответствующими полями, как при клиентской проверке. Фокус на первом ошибочном поле, в живой области «Проверьте отмеченные поля. Ошибок: N» |
| Сеть недоступна | «Не удалось связаться с сервером. Проверьте подключение к интернету и попробуйте ещё раз.» |
| Ошибка сервера (`500` при сбое базы, другой `5xx`, не JSON, `400` без ошибок по полям) | «Сервер не смог обработать заявку. Попробуйте отправить её ещё раз чуть позже.» |

- При любой ошибке введённые значения сохраняются.
- **Кнопка «Очистить форму»** появляется после успешной отправки. Она сбрасывает значения, ошибки и сообщение и переводит фокус на первое поле. Если после успеха изменить любое поле, сообщение об успехе скрывается, а кнопка отправки снова становится доступной.
- **Общий тип ответа** `ApplicationApiResponse` лежит в `applicationSchema.ts`. Роут проверяет свои ответы по нему через `satisfies`, клиент разбирает ответ по тому же типу.


### Общая схема заявки

`src/lib/applicationSchema.ts` — единственный источник правил:

| Поле | Правило в схеме | Сообщения |
| --- | --- | --- |
| `founderName` | строка, `trim`, 2–80 | «Укажите имя основателя.» / «Имя должно содержать от 2 до 80 символов.» |
| `email` | строка, `trim`, до 254, `z.email()` | «Укажите email для связи.» / «Email не должен быть длиннее 254 символов.» / «Проверьте email — он должен выглядеть как name@example.com.» |
| `projectName` | строка, `trim`, 2–120 | «Укажите название проекта.» / «Название должно содержать от 2 до 120 символов.» |
| `stage` | `z.enum(["idea", "prototype", "mvp", "early_users"])` | «Выберите стадию проекта.» (пусто) / «Выберите стадию из списка.» (неизвестное значение) |
| `problem` | строка, `trim`, 10–1000 | «Опишите проблему, которую решает проект.» / «Описание должно содержать от 10 до 1000 символов.» |
| `demoUrl` | необязательная строка, `trim`, до 2048; пустая строка допустима, непустая — URL с `http://` или `https://` | «Укажите полную ссылку, которая начинается с http:// или https://.» / «Ссылка не должна быть длиннее 2048 символов.» |

Как устроены сообщения:

- Сообщение «заполните» выдаётся и для пустой строки, и для отсутствующего поля или значения другого типа.
- Для пустой строки возвращается только оно, без сообщения о длине (`abort: true`).
- Если в поле придёт массив вместо строки, Zod может вернуть одно и то же сообщение дважды. Через форму такой запрос не отправить, первое сообщение остаётся корректным.

Экспорт модуля:

- `applicationSchema`, `limits`, `stages`, `stageLabels`;
- типы, выведенные из схемы: `ApplicationInput` (`z.input`), `Application` (`z.output`, значения после `trim`), `ApplicationField`, `ApplicationFieldErrors`, `Stage`;
- тип ответа API `ApplicationApiResponse`.

### API `POST /api/applications`

✅ `src/app/api/applications/route.ts` — стандартный Route Handler App Router в Node.js runtime (по умолчанию; `sqlite3` в браузере и Edge не работает).

Роут отвечает только за HTTP-слой:

1. Разбирает JSON.
2. Проверяет тело общей схемой через `applicationSchema.safeParse`.
3. Передаёт проверенные данные в `saveApplication` из `src/lib/db.ts`.
4. Формирует ответ.

| Запрос | Ответ |
| --- | --- |
| Корректная заявка, запись в базу завершена | `201` — `{ "success": true, "message": "Заявка успешно отправлена" }` |
| Ошибки в полях, отсутствующие поля, не объект (например, массив) | `400` — `{ "success": false, "message": "Проверьте данные заявки.", "errors": { "<поле>": ["сообщение", …] } }` |
| Некорректный JSON, пустое тело, не JSON | `400` — `{ "success": false, "message": "Некорректный JSON в теле запроса." }` |
| Ошибка базы (не удалось открыть или записать) | `500` — `{ "success": false, "message": "Не удалось сохранить заявку. Попробуйте отправить её ещё раз чуть позже." }` |
| Любой метод, кроме `POST` | `405` (Next.js отвечает автоматически) |

Подробности:

- В базу попадают только данные, прошедшие серверную Zod-проверку, со значениями после `trim`.
- `201` возвращается только после того, как SQLite подтвердил запись.
- Повторная отправка одинаковой заявки создаёт новую запись: дубликаты не отсекаются.
- `errors` — это `z.flattenError(...).fieldErrors`: только сообщения по полям схемы. Если пришёл не объект, `errors` пустой, а общий смысл передаёт `message`.
- Неизвестные поля в запросе игнорируются: `z.object` их отбрасывает.
- При ошибке базы подробности (например, `SQLITE_READONLY`) пишутся только в лог сервера через `console.error`. Клиент получает безопасное сообщение.

Ручная проверка при запущенном `npm run dev`.

macOS (Terminal):

```bash
curl -i -X POST http://localhost:3000/api/applications \
  -H "Content-Type: application/json" \
  -d '{"founderName":"Анна","email":"anna@example.com","projectName":"Vibe Notes","stage":"mvp","problem":"Командам поддержки трудно находить ответы.","demoUrl":""}'
```

Windows (PowerShell). Пример на встроенном `Invoke-RestMethod`; кириллица передаётся в UTF-8:

```powershell
$body = @{
  founderName = "Анна"; email = "anna@example.com"; projectName = "Vibe Notes"
  stage = "mvp"; problem = "Командам поддержки трудно находить ответы."; demoUrl = ""
} | ConvertTo-Json
Invoke-RestMethod -Method Post -Uri http://localhost:3000/api/applications `
  -ContentType "application/json; charset=utf-8" `
  -Body ([System.Text.Encoding]::UTF8.GetBytes($body))
```

Чтобы проверить ответ `400`, отправьте битый JSON: в macOS, например, `-d '{"founderName":'`, в PowerShell — `-Body '{"founderName":'`. На ответ `400` `Invoke-RestMethod` выводит ошибку с текстом сообщения сервера.

### Хранение в SQLite

✅ Работа с базой вынесена в серверный модуль `src/lib/db.ts`.

- **Файл базы:** `data/app.db`. Он и служебные файлы SQLite (`-journal`, `-wal`, `-shm`) в Git не попадают: правила `/data/` и `/data/app.db*` в `.gitignore`.
- **Автоматическое создание:** при первом сохранении модуль создаёт папку `data/` (`mkdirSync` с `recursive`) и таблицу (`CREATE TABLE IF NOT EXISTS`). Формальных миграций нет.
- **Подключение:** одно на процесс сервера. Если открыть базу не удалось, следующий запрос попробует снова.
- **Сохранение:** `saveApplication(application)` выполняет параметризованный `INSERT` с плейсхолдерами `?`, без склейки строк. Промис разрешается только после завершения записи и возвращает `id` новой записи.
- **Защита от клиентского импорта:** модуль начинается с `import "server-only"`, поэтому при импорте в клиентский компонент сборка упадёт.
- **Настройка Next.js:** `sqlite3` входит в стандартный список внешних серверных пакетов Next.js, отдельная настройка в `next.config.ts` не нужна.

Схема таблицы:

```sql
CREATE TABLE IF NOT EXISTS applications (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  founder_name TEXT NOT NULL,
  email        TEXT NOT NULL,
  project_name TEXT NOT NULL,
  stage        TEXT NOT NULL,  -- idea | prototype | mvp | early_users
  problem      TEXT NOT NULL,
  demo_url     TEXT,           -- NULL, если ссылка не указана
  created_at   TEXT NOT NULL   -- UTC в ISO 8601, например 2026-10-21T20:50:53.934Z
);
```

- `created_at` заполняет приложение через `new Date().toISOString()`, а не SQLite. Поэтому формат ISO 8601 UTC одинаков для всех записей.
- Пустая ссылка на демо сохраняется как `NULL`.
- Посмотреть записи на macOS (консольный `sqlite3` установлен в системе):

```bash
sqlite3 -header -column data/app.db "SELECT id, founder_name, email, stage, created_at FROM applications"
```

- На Windows консольного `sqlite3` по умолчанию нет. Работает команда из раздела [Проверка проекта](#проверка-проекта) через `node -e`, она открывает базу только для чтения и подходит для обеих систем.

- Чтобы начать с пустой базой, остановите сервер и удалите `data/app.db`: при следующей заявке файл создастся заново. Все сохранённые заявки при этом пропадут.

### CSV-выгрузка

✅ Node.js-скрипт `scripts/export-applications.mjs`, запускается командой `npm run export:csv`. Новых зависимостей нет: используется уже установленный `sqlite3`, CSV формируется вручную.

- **Источник:** таблица `applications` из `data/app.db`. База открывается в режиме `OPEN_READONLY`: скрипт ничего в ней не меняет и не создаёт новую базу вместо отсутствующей.
- **Результат:** один файл `exports/applications.csv`. Папка `exports/` создаётся автоматически. Каждый запуск перезаписывает файл целиком актуальными данными. Файл содержит реальные заявки и в Git не попадает.
- **Пример в репозитории:** `exports/sample-applications.csv` — четыре полностью вымышленные заявки. Он получен этим же скриптом на отдельной временной базе, рабочая `data/app.db` не использовалась. В `.gitignore` содержимое `exports/` исключено, кроме этого файла (`!/exports/sample-applications.csv`).
- **Пути** строятся через `path.join` от расположения скрипта. Команда одинаково работает на macOS и Windows и не зависит от текущей папки терминала.
- **Столбцы:** `id, founder_name, email, project_name, stage, problem, demo_url, created_at`, первая строка — заголовки. Записи отсортированы по `id`.
- **Формат** по RFC 4180:
  - разделитель — запятая, строки разделяются `CRLF`;
  - значение с запятой, кавычкой или переносом строки берётся в двойные кавычки, кавычки внутри удваиваются: `Иван, "Ваня"` → `"Иван, ""Ваня"""`;
  - переносы строк внутри значения сохраняются как есть;
  - `NULL` (пустой `demo_url`) выгружается пустой ячейкой.
- **Кодировка:** UTF-8 с BOM, чтобы Excel распознал кодировку и правильно показал кириллицу.
- **После выгрузки** скрипт выводит количество строк и полный путь к файлу:

  ```text
  Выгружено заявок: 69
  Файл: /Users/…/vibe-venture/exports/applications.csv
  ```

| Ситуация | Поведение | Код выхода |
| --- | --- | --- |
| Есть заявки | CSV с заголовками и всеми записями | `0` |
| Таблица пустая | CSV только со строкой заголовков, «Выгружено заявок: 0» | `0` |
| Нет файла `data/app.db` | «База данных не найдена…» с подсказкой отправить заявку; база не создаётся | `1` |
| Файл базы есть, таблицы нет | «В базе … нет таблицы applications…» | `1` |
| Не удалось записать CSV (например, файл открыт в Excel на Windows) | Сообщение с просьбой закрыть файл и повторить | `1` |

Ошибки выводятся понятным сообщением, без необработанного исключения и стека.

## Визуальная концепция

**Референс:** скриншоты сайта Google Ventures (GV), которые предоставил автор проекта.

**Направление:** bold editorial, швейцарская типографика, элементы neo-brutalism.

### Что берём из референса

- Очень крупная узкая типографика. Заголовки занимают почти всю ширину экрана.
- Тяжёлые заголовки в верхнем регистре с плотным межбуквенным интервалом и плотным интерлиньяжем.
- Почти белый фон и почти чёрный текст.
- Жёлто-оранжевые акценты: плашки категорий, CTA, отдельные графические элементы.
- Строгая модульная сетка и выразительная асимметрия: крупный заголовок слева, плотный текстовый блок справа.
- Много пустого пространства.
- Светлые и чёрные полноширинные секции чередуются.
- Геометрическая графика из линий, точек и простых форм (как точечная диаграмма на чёрном фоне в референсе).
- Типографские приёмы: приглушённые и активные строки списка, крупные скобки, мелкие подписи рядом с крупным заголовком.
- Минимум скруглений, теней, градиентов и декоративных эффектов.

### Палитра

Токены задаются в Tailwind-теме (`bg-orange`, `text-yellow`, `border-muted` и т. д.). В компонентах цвета не хардкодятся.

Правила применения цвета:

- Оранжевый — только заливки (основная кнопка, «Подать заявку» в шапке, маркеры), подчёркивания ссылок и крупные декоративные знаки. На светлом фоне оранжевый текст не используется: его контраст ниже 3:1.
- Жёлтый — метка EARLY-STAGE AI, выделенное слово на чёрном фоне, лента-переход перед формой, открытый вопрос в FAQ, номера на `/about`.
- `muted` — только декоративные элементы: огромные «призрачные» номера 01–04 в «Плюсах». Они скрыты от скринридеров, порядок передаёт `<ol>`.
- Второстепенный текст — `foreground` или `background` с прозрачностью 60–80%. Контраст не ниже WCAG AA.

### Типографика

- **Заголовки:** Oswald Bold (узкий гротеск с кириллицей).
- **Основной текст:** Inter (с кириллицей).
- **Подключение:** вариативные `.woff2` лежат в `src/app/fonts/` и подключаются через `next/font/local`. Сеть не нужна ни при сборке, ни во время работы.
  - Файлы собраны из исходников репозитория google/fonts. В них оставлены латиница, кириллица, типографская пунктуация, ось насыщенности 400–700, а у Inter оптический размер зафиксирован на 14. Размеры: Oswald около 28 КБ, Inter около 54 КБ.
  - Лицензии OFL лежат рядом: `OFL-Oswald.txt` и `OFL-Inter.txt`.
  - В Oswald нет символа стрелки «→», поэтому стрелки набираются Inter (класс `.arrow`).

## Архитектурные принципы

- **TypeScript** в строгом режиме, без необоснованного `any`.
- **Server Components по умолчанию.** Client Components (`"use client"`) только там, где нужна интерактивность. Сейчас клиентский компонент один — `ApplicationForm`. FAQ работает на `<details>`, мобильная навигация на CSS.
- **Отдельные компоненты** для навигации, каждой основной секции и формы.
- **Одна Zod-схема** в `src/lib/applicationSchema.ts` для клиента и сервера. Типы заявки выводятся из неё (`z.input` / `z.output`), лимиты и тексты ошибок нигде не дублируются.
- **Отдельный серверный модуль для SQLite** (`src/lib/db.ts`) с `import "server-only"`: он не может попасть в клиентский код.
- **Семантическая разметка:** `header`, `nav`, `main`, `section` с заголовками, `footer`, `label` для каждого поля.
- **Доступность:** полная работа с клавиатуры, видимый фокус, ссылка «Перейти к содержимому», корректная иерархия заголовков, учёт `prefers-reduced-motion`.
- **Адаптивность:** mobile-first. Крупная типографика масштабируется (`clamp()`) и не вызывает горизонтальной прокрутки.
- **Минимум зависимостей.** Каждая новая зависимость должна быть обоснована.
- **Без абстракций ради абстракций.** Простой и прямой код лучше преждевременных обобщений.

Как устроен интерфейс:

- Все компоненты серверные, кроме `ApplicationForm` (`"use client"`): ей нужно состояние.
- Header и Footer подключены в `layout.tsx`. Страницы только собирают секции.
- Тексты лежат прямо в компонентах. Короткие списки хранятся в массивах внутри своего компонента.
- Чередование фона на главной: hero светлый, «О нас» чёрный, «Плюсы» светлый, «Вопросы» чёрный, жёлтая лента, «Форма» светлая, подвал чёрный.
- Композиции разные:
  - hero — двухстрочный заголовок, графика справа от VIBE, текст и CTA в правой половине;
  - «О нас» — заголовок на 8 колонок, текст на 4;
  - «Плюсы» — нумерованные строки 3 + 5 + 4;
  - «Вопросы» — огромный заголовок, аккордеон справа;
  - «Форма» — заголовок, текст на 4 колонки, форма на 7.
- На `/about` своя композиция: заголовок прижат вправо, разделы в сетке 4 + 7 с колонкой-индексом, «Как помогаем» на чёрной полосе 2 × 2, отбор показан четырьмя шагами.
- Каждая секция главной начинается с метки `(01) — …`: это редакционная нумерация.

Что важно знать о `next.config.ts`:

- `agentRules: false` — запрещает `next dev` создавать `AGENTS.md`. Инструкции для ИИ-ассистента хранятся в этом README.
- `cacheComponents: true` и `partialPrefetching: true` — значения шаблона Next.js 16. Пока оставлены как есть. Это нужно учитывать при работе с динамическими данными.
- Правило `turbopack` с `@tailwindcss/turbopack` — так шаблон подключает Tailwind CSS 4.

## Ограничения MVP

- Только локальный запуск, без деплоя.
- Нет авторизации и админ-панели. Заявки доступны только через CSV-выгрузку.
- Нет отправки писем и уведомлений.
- Нет защиты от спама и rate limiting.
- Нет формальных миграций: схема создаётся через `CREATE TABLE IF NOT EXISTS`. При изменении схемы локальную базу можно удалить.
- Нет загрузки файлов. Демо передаётся только ссылкой.
- Один язык интерфейса — русский.
- Контент вымышленный: никаких реальных сделок, сумм, сроков и гарантий.
- SQLite рассчитана на одного локального пользователя, конкурентная нагрузка не рассматривается.

## Запуск на macOS

> Сейчас по этой инструкции запускается приложение со страницами `/` и `/about`. Форма сохраняет заявки в локальную базу `data/app.db`.

**Требования:** Node.js 22 LTS или 24 LTS (минимум 20.17 — его требует пакет `sqlite3`, Next.js 16 требует 20.9; на нечётных версиях, например 23.x, `npm install` выводит предупреждения `EBADENGINE`) и npm (устанавливается вместе с Node.js).

1. Проверьте версии:

   ```bash
   node -v
   npm -v
   ```

   Если Node.js не установлен, скачайте LTS-версию с [nodejs.org](https://nodejs.org/) или установите через Homebrew: `brew install node`.

2. Склонируйте репозиторий и перейдите в папку проекта:

   ```bash
   git clone <url-репозитория> vibe-venture
   cd vibe-venture
   ```

3. Установите зависимости:

   ```bash
   npm install
   ```

   Пакет `sqlite3` обычно ставится из готовых бинарников. Если установка упадёт с ошибкой сборки, установите Xcode Command Line Tools (`xcode-select --install`) и повторите `npm install`.

4. Запустите dev-сервер:

   ```bash
   npm run dev
   ```

5. Откройте [http://localhost:3000](http://localhost:3000). Файл `data/app.db` создаётся при первой отправке заявки.

Остановить сервер: `Ctrl + C` в терминале.

## CSV-выгрузка на macOS

1. Убедитесь, что хотя бы одна заявка отправлена через форму, то есть база `data/app.db` существует.
2. Из корня проекта выполните:

   ```bash
   npm run export:csv
   ```

3. Скрипт выведет количество заявок и путь к файлу `exports/applications.csv`. При повторном запуске файл перезаписывается.
4. Откройте файл:

   ```bash
   open exports/applications.csv
   ```

Dev-сервер для выгрузки останавливать не нужно: скрипт только читает базу.

## CSV-выгрузка на Windows

> Команды приведены для PowerShell. На Windows скрипт пока не проверялся.

1. Убедитесь, что хотя бы одна заявка отправлена через форму, то есть база `data\app.db` существует.
2. Из корня проекта выполните:

   ```powershell
   npm run export:csv
   ```

3. Скрипт выведет количество заявок и путь к файлу `exports\applications.csv`. При повторном запуске файл перезаписывается. Перед повторной выгрузкой закройте файл в Excel: Windows не даёт перезаписать открытый файл, и скрипт сообщит об этом.
4. Откройте файл:

   ```powershell
   Invoke-Item exports\applications.csv
   ```

Dev-сервер для выгрузки останавливать не нужно: скрипт только читает базу.

Если Excel неправильно разбивает файл на столбцы (в русской локали Excel по умолчанию ожидает разделитель `;`), импортируйте его через «Данные → Из текстового/CSV-файла» и укажите разделитель «запятая» и кодировку UTF-8.
